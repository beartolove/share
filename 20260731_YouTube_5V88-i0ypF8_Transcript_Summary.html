模型再強也沒用：GPT-5.6 翻車背後的系統設計致命缺陷

一句話總結

這支影片用 GPT-5.6-Sol 刪除使用者 Mac 檔案的事件，說明 AI Agent 的可靠性不只取決於模型能力，更取決於外層的 Harness Engineering：權限邊界、沙箱、審批、記憶、流程與驗證機制。

重點摘要

  1. 事故重點不是「模型怎麼這麼笨」，而是高風險命令為什麼能越過權限邊界、審批與沙箱，直接作用到真實檔案系統。
  2. Agent 可以理解為「model + harness」。模型負責推理與生成，harness 則包含工具、記憶、權限、驗證、編排邏輯與安全護欄。
  3. 只靠提示詞無法穩定控制 Agent。提示詞能改善一部分行為，但無法取代工程上的權限隔離、流程規範與失敗保護。
  4. 影片指出三個核心痛點：上下文擁擠、缺乏流程規範、缺乏安全邊界。這些問題都需要由外部系統設計處理，而不是只期待模型自己記得。
  5. 好的 Harness 不是限制 AI 創造力，而是讓 AI 在正確方向上發揮能力，並讓輸出安全、可靠、可維護。

關鍵觀察

  • 上下文不能無限制塞滿所有歷史、程式碼與需求；重要約束會被淹沒。更好的做法是把記憶外包成結構化檔案、日誌與檢索機制。
  • 工作流程不能每次都讓模型重新生成；要把步驟、停止條件、測試要求與驗收標準外部化。
  • 高風險工具呼叫需要分級審批與執行環境隔離，例如檔案刪除、批次改寫、系統命令與網路操作。
  • Agent 需要可觀測性：每一步做了什麼、為什麼做、改了哪些檔案、測試結果如何，都應留下紀錄。

適合使用情境／可延伸思考

  1. 企業導入 AI Agent 時，應先設計權限模型、沙箱、審批門檻與可回復機制，再開放代理人操作內部系統。
  2. 工程團隊使用 Claude Code、Codex 或其他 coding agent 時，應把測試、版本控制、檔案範圍與危險命令攔截納入標準流程。
  3. 個人使用 AI 寫程式時，也應避免給 Full Access 後直接放手，至少要搭配 Git、備份、diff review 與明確的工作目錄限制。
  4. 評估 AI Agent 能不能上線，不只看模型 benchmark，也要看 harness 是否能處理記憶、流程、安全、驗證與追蹤。
