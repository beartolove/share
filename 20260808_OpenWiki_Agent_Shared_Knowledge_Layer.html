OpenWiki：Agent 時代的共用知識層

OpenWiki 不只是自動產生 Wiki 的 CLI，更像是在 Agent 時代把「知識」從單一模型、單一 Agent、單一平台中抽離出來的一層基礎設施。

重點摘要

  • 問題意識：Agent 越來越多，但知識不應該被綁在單一 Agent 的私有 Memory 裡。
  • 核心差異：RAG 偏向每次提問重新找片段；LLM Wiki 偏向把理解持續寫成可連結、可更新的 Markdown。
  • OpenWiki 的角色：它把不同來源整理成 Wiki，讓人與不同 Agent 都能讀同一套知識。
  • 關鍵價值：模型可以換、Agent 可以換，但 Knowledge Layer 應該由使用者擁有並可攜。
  • 成熟度提醒：Connector、權限、同步與跨 Agent API 還有成長空間，但方向已經很清楚。

為什麼這不是普通 Wiki 工具？

資料來源分散Notion、Gmail、Slack、GitHub、X、本地文件與程式碼庫。
Agent 也分散Claude Code、Codex、Cursor、Hermes Agent 或自建 Agent。
中間需要一層獨立、可攜、可版本化、可被多 Agent 讀取的知識層。
OpenWiki 的切入點把理解整理成互相連結的 Markdown Wiki。

RAG、LLM Wiki、OpenWiki 的差別

面向傳統 RAGLLM WikiOpenWiki 的定位

產物型態臨時組合的回答互相連結的知識頁面使用者擁有的 Markdown 文件
與 Agent 關係多半服務當次問答可變成長期可讀的知識庫降低對單一 Agent 或平台的綁定
適合場景文件問答、查詢輔助長期知識累積與更新程式碼庫文件、個人知識、團隊知識基礎設施

OpenWiki 可以做什麼？

多來源讀取

貼文指出可讀取 Notion、Gmail、Slack、X、Web Search 與本地 Git Repo；官方 README 也列出 Notion、Slack、Gmail、X/Twitter、Web Search、Hacker News、Local git repositories 等 Connector。

兩種 Wiki 模式

官方 README 說明支援 code mode 與 personal mode：可以為目前 repo 產出 openwiki/，也可以為個人來源產出 ~/.openwiki/wiki。

多模型供應商

支援 OpenAI、Anthropic、Gemini、Bedrock、OpenAI-compatible gateways、Copilot 等不同模型路徑，降低模型鎖定。

自動更新與視覺化

可透過 GitHub Actions、GitLab CI、Bitbucket Pipelines 自動更新，也提供本地 visualizer 讓人用知識圖譜瀏覽 Wiki。

架構啟發：Knowledge Layer 應該獨立

模型可以換，Agent 可以換，但知識層不能跟著一直搬家。

這篇貼文真正值得關注的地方，不只是 OpenWiki 這個工具本身，而是它把「知識屬於誰」這件事重新拉回使用者手上。若知識長期只存在某個 Agent 的私有 Memory 裡，換工具、換模型、換工作流時，就會不斷搬家、重建、流失上下文。

以 Markdown、Git、CI 與開放格式為核心的 Knowledge Layer，則比較接近一種可攜的個人或團隊知識作業系統。

目前限制與觀察

  • Connector 覆蓋度還需要持續擴充，尤其是企業內部系統與權限複雜的資料源。
  • 權限控管、即時同步、跨 Agent API 仍會是走向正式知識基礎設施前的重要課題。
  • Markdown 可攜是優點，但也代表團隊需要建立命名、連結、版本、審稿與更新規則。
  • 如果未來不同 Agent 都能讀取同一套 Open Knowledge Format，Agent 生態才可能真正降低平台鎖定。

快速試用

npm install -g openwiki
openwiki --init

openwiki visualize

原文整理

最近 LangChain 開源了一個我認為非常值得關注的項目：OpenWiki。

表面上，它是一個可以自動建立與維護 Wiki 的 CLI 工具。

但我覺得它真正重要的地方，是開始解決 Agent 時代的一個底層問題：
我們的知識，究竟應該屬於哪一個 AI Agent？

最近 Karpathy 提出的 LLM Wiki 概念很受關注。

它與傳統 RAG 最大的差別是：
RAG 每次提問，都重新從原始文件中搜尋片段，再臨時組合答案。

LLM Wiki 則是讓 AI 持續閱讀資料，將理解寫成互相連結的 Markdown 頁面，並隨著新資料持續修正與更新。

簡單來說：
RAG 是每次重新找答案；LLM Wiki 是把理解累積下來。

目前已經出現不少相關開源實作，包括 Karpathy LLM Wiki Skill、Graphify 等。

但很多工具仍依賴 Claude Code、Codex、Cursor 或其他 Agent 裡的 Skill 執行。

這會產生一個問題：
當知識庫的建立與維護依賴某個 Agent，我們就很容易和那個 Agent 深度綁定。

但現實中，我們的知識通常分散在：
・Notion
・Obsidian
・Gmail
・Slack
・GitHub
・X
・本地文件與程式碼庫

同時，我們使用的 Agent 也可能不只一個：
今天用 Claude Code，明天用 Codex，還可能有 Hermes Agent、Cursor 或自己開發的 Agent。

OpenWiki 的價值，就是試圖在兩者之間建立一層獨立的知識基礎設施。

它本身是一個獨立 CLI，可以：
・讀取 Notion、Gmail、Slack、X、Web Search 與本地 Git Repo
・把不同來源整理成互相連結的 Markdown Wiki
・為程式碼庫或個人知識分別建立 Wiki
・透過 GitHub Actions、GitLab CI 自動更新
・使用 OpenAI、Claude、Gemini、Bedrock、Copilot、Ollama 等不同模型
・將知識輸出成開放的 Open Knowledge Format
・讓人類透過視覺化知識圖譜瀏覽

最重要的是，產出的不是鎖在某個平台裡的專有資料，而是自己擁有的 Markdown 文件。

這讓不同 Agent 都可以共同讀取同一套知識。

我認為未來比較合理的 Agent 架構，應該是：
模型可以換，Agent 可以換，但知識層不能跟著一直搬家。

我們需要的不是某個 Agent 私有的 Memory。

而是一個：
獨立於模型、獨立於 Agent、由使用者真正擁有的 Knowledge Layer。

OpenWiki 現在還不是完整終局。

它的 Connector、權限管理、即時同步和跨 Agent API 都還有很大的成長空間。

但它已經把「Agent 共用知識層」這個方向，做成了一個可以真正開始使用的開源工具。

截至目前，專案推出約一個半月，GitHub 已超過 1.4 萬 Stars。

這可能不只是一個 Wiki 工具。

它更像是 Agent 時代「個人知識作業系統」的早期雛形。
