重點摘要

  • 這是一個互動式 LLM 推論基礎設施視覺化工具，目標是幫助理解 GPU 算力、記憶體頻寬、KV Cache、上下文長度、Batch Size 與多 GPU 擴展之間的關係。
  • Live Demo 與 README 都強調：它是教育與直覺建立工具，不是 production-grade benchmark 或精準效能模擬器。
  • 核心功能包含 Roofline 瓶頸分析、多 GPU / Tensor Parallelism / MoE 通訊視覺化、KV Cache 多級儲存經濟學，以及內建小 Z AI 助手。
  • 工具用純前端 HTML/CSS/JavaScript 實作，可直接在瀏覽器使用；圖表與數學公式依賴 Chart.js 與 KaTeX。
  • 小 Z 助手需自備 OpenAI-compatible API Endpoint、API Key 與模型名稱，才能透過對話控制面板參數。

小河提醒：這類工具最適合拿來建立「推論瓶頸會轉移」的直覺；正式採購或容量規劃仍要搭配真實 workload benchmark。

核心概念對照

Roofline Model把每一步推論延遲拆成算力時間與記憶體讀取時間，觀察何時 compute-bound、何時 memory-bound。
KV Cache長上下文與多輪對話會讓快取佔用大量 HBM，進而影響同時服務的請求數與成本。
Batch SizeBatch 變大可能提高吞吐，但也會改變算力、頻寬、快取佔用與延遲的平衡。
Multi-GPU Scaling模型太大或 KV Cache 太多時需要分片，但跨 GPU / 跨機架通訊會變成新瓶頸。
MoE Routing稀疏激活降低 active parameters，但專家路由與 All-to-All 通訊會增加系統複雜度。

可以怎麼用？

  1. 先用預設參數觀察 Roofline 與瓶頸狀態。
  2. 調整 Batch Size 與 Context Length，觀察 throughput、延遲與 KV Cache 壓力如何變化。
  3. 切換 Dense / MoE 與多 GPU 參數，理解通訊成本為什麼會變成瓶頸。
  4. 比較 HBM、DDR、SSD 與 Remat 的快取策略，建立成本／延遲／容量取捨直覺。
  5. 若要使用小 Z 助手，需自行提供 OpenAI-compatible API 設定。

原文整理

最近在研究 LLM inference infrastructure，看了 Reiner Pope 的訪談後，為了幫自己理解 GPU 運算、Memory Bandwidth、KV Cache、Context Length、Batch Size、Multi-GPU scaling 之間的關係，就做了一個互動式的 LLM Infra Visualizer。

原本只是拿來自己學習，也分享給公司同事試用，大家覺得滿有幫助，所以就整理成公開版本，讓有興趣的人可以直接在瀏覽器上玩玩看。

這不是精準的 production benchmark，而是希望用視覺化的方式，讓 LLM inference 背後的一些概念更容易理解。
