重點摘要

  • Harness 管環境：包含 system prompt、工具定義、記憶、沙箱、權限、日誌、上下文壓縮與路由；工程環境爛，換更強模型也救不了。
  • Loop 管反饋：當結果不穩、無界重試、成功也不停手或沒有證據就收工時，應補上外部評分器、確定性測試、有界重試與證據驅動停止規則。
  • Graph 管流程：只有在多專家協同、條件分支、並行執行、多級審批或錯誤恢復路徑明確時，才需要把流程顯式畫成圖。
  • 最有用的是排障決策表：把「Agent 怎麼又抽風」這種模糊抱怨，翻成工程師可以執行的排查工單。
  • 七條可直接落地的實踐包含：證據驅動停止、有界重試、最小權限、進度檔案＋Git 持久化、確定性檢查優先、先跑 trace 再畫 Graph、工具寧窄勿寬。
  • 三個坑要避開：Graph 過早儀式化、術語包裝通膨、廠商敘事夾帶推廣私貨。
  • 影片最後提醒：Loop 只適合用在失敗成本遠高於驗證成本的地方；其餘位置，最簡單架構通常才是最正確架構。

提醒：這是工程排障思維整理，不是特定框架採購建議；影片提到的 X 瀏覽／收藏數會隨時間變動。

一句話總結

這支影片把 Agent 系統故障拆成 Harness、Loop、Graph 三層，主張不要一出事就怪模型，而要用「症狀到分層」的方式定位環境、反饋或流程問題。

關鍵數字／觀察

  • 原文在 X 上約 58 萬瀏覽、6.5 萬收藏。
  • 典型事故：Agent 重試 20 次、token 帳單翻三倍，bug 還在原地。
  • 決策模型：環境出毛病修 Harness；反饋不閉環修 Loop；流程卡殼修 Graph。

可落地檢核表

  • 停止條件是否有證據：測試通過、URL 可解析、schema 校驗通過或人工審批。
  • 每個循環是否有明確目標、新證據、最大重試次數與兜底路徑。
  • 工具、網路、API key 與人工作業是否遵守最小權限。
  • 進度是否寫入結構化檔案與 Git 歷史，而不是只靠上下文記憶。
  • 評估是否優先使用確定性測試，而不是讓模型自評。
  • Graph 是否由真實 trace 驗證後再固化，而不是早期需求未定就先畫大圖。
  • 工具集是否寧窄勿寬，避免把 Harness 變成垃圾場。

給團隊的提醒

  • 不要把所有 Agent 事故都歸咎於「模型不夠聰明」。
  • 先把症狀翻成 Harness／Loop／Graph 的工程問題，再決定要修環境、反饋或流程。
  • 傳統 SRE、資安與測試工程紀律，在 Agent 時代仍然是核心護城河。
