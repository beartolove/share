ChatGPT Pro 接 GitHub：把上游規劃交給 GPT，本地執行交給 Codex

這篇分享的是一種 agentic workflow：讓網頁版 ChatGPT Pro 連接 GitHub，擔任上游架構規劃者與 PR 產生者；本地端則交給 Codex 或便宜快速的 agent 做實際執行、測試與修正。

重點摘要

  • 核心轉變：GPT Pro 接上 GitHub 後，不只讀幾段程式碼，而是能理解整個 repository 的架構、規則與既有程式碼。
  • 實際落差：原本只是請它規劃小工具，結果它可能一路完成程式、branch、commit 與 draft PR。
  • 最大誘因：貼文觀察到 GPT Pro 工作超過一小時，訂閱 token 額度看起來沒有變動。
  • 重要限制：這不是穩定保證；ChatGPT Pro 對話模式仍有不可見額度，OpenAI 政策也可能改變。
  • 落地做法：GPT Pro 做上游規劃與 GitHub 變更，本地 Codex／agent 負責環境差異、測試、修正與驗證。

工作流拆解

階段適合交給誰重點風險提醒
讀專案與規劃ChatGPT Pro + GitHub理解 repo、規則、README、既有程式碼。不要授予不必要的寫入權限。
產生變更ChatGPT Pro 或上游代理建立 branch、commit、draft PR。避免直接合併；以草稿 PR 保留審查關卡。
本地執行Codex／本地 agent跑測試、補依賴、修環境差異。GPT 看不到本機未提交變更與工具鏈狀態。
審查合併人類與團隊確認安全性、架構一致性與可維護性。token 額度與 ChatGPT 隱藏限制不可視為永久免費。

小河觀察

這個流程最值得學的不是「免費用 token」，而是把 AI 工作拆成上下游：上游負責脈絡、架構與 PR；下游負責本地驗證、測試與修正。真正安全的關鍵，是權限最小化、draft PR、人類審查與本地測試。

原文整理

在 Codex 社群裡，最近很常看到一種玩法：把網頁版的 ChatGPT Pro 當成上游的 AI 代理與架構規劃者，負責思考整體方向，再讓 Codex 在自己的電腦上實際執行。而其中一個很好用的橋樑，就是把 GitHub 接到 ChatGPT。

接上 GitHub 之後，GPT 就不再只能根據你複製貼上的幾段程式碼回答問題，而是可以直接讀取你的整個程式專案（repository），了解目前的專案架構、規則、說明文件，以及已經存在的程式碼。

而在我目前使用的 ChatGPT 環境裡，GitHub 不只有讀取能力，也提供了一些寫入功能。

剛才我原本只是想請 GPT Pro 幫我規劃一個小工具，心裡預期它大概就是分析一下需求，再寫一份計畫書給我。

結果它先自己去讀了我的 GitHub 專案和既有規則，接著直接把整套程式寫了出來，建立新的程式分支（branch）、完成版本提交（commit），最後甚至幫我開好一個草稿合併請求（draft PR），讓其它人可以先檢查內容，再決定要不要正式合併。

換句話說，我原本只是叫它：「想一想這個東西應該怎麼做。」

結果它自己一路做到：「程式已經寫好了，也放進 GitHub 了，現在等你檢查。」

這件事情當然有它明顯的缺點，社群裡也有很多人提醒過，因為 GPT Pro 無法總覽你的本地環境，因此若專案是要在本地施行的，那勢必會存在落差。

但因為這件事的優點實在是太強大了，所以可以讓多數人無視其缺點。

什麼優點呢？就是不消耗訂閱的 token 額度。

剛才 GPT Pro 工作了超過一小時，我實際觀察，token 消耗完全沒有變動。而且經過 GPT Pro 的鋪路，本地端只要用便宜快速的 agent 來實作就可以了。

另外提醒，對話版本的 GPT Pro 有它自己的獨立額度，只是這個數字是看不到的。

（我曾經把 GPT Pro 拿來當掃地工，被 Codex Luna 拿鞭子使喚，結果最後就撞牆跳警告視窗）
