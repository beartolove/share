重點摘要

1

John Bai 用 Grok Bot 來設計 Grok Bot 本身，重點不是把設計判斷交給 AI，而是讓想法更快變成可操作原型。

2

四個 AI 設計 Agent 各有角色：Experiments 探索概念，Motion God 做動態，Figma Bro 處理 Figma 生產工作，Devbot 補工程判斷。

3

Agent 之間可以互相開會、分派任務、整合成果，形成一個可持續運作的設計團隊，而不只是單一聊天工具。

4

三個案例分別展示：環境 Bot 入口探索、用真實素材建立動態原型、透過 Figma MCP 精準完成重複性設計生產。

5

最重要的啟發是：AI Agent 壓縮了「做出來 → 看反應 → 修改」的循環，讓設計師把注意力放在版本判斷與品味選擇上。

四個 Agent 的分工

Experiments

把尚未定型的想法具象化，快速做出可試用的概念原型。

Motion God

用口語描述互動感覺，搭配真實生產素材做動態原型。

Figma Bro

透過 Figma MCP 讀取實際座標、元件、間距與樣式，處理重複生產工作。

Devbot

回答工程問題，協助其他 Agent 理解技術限制與實作方式。

三個案例

環境 Bot 入口

探索 Mac 瀏海、桌面角落探頭、游標隨行三種呼叫方式。

真實素材做動態

在 localhost 建測試環境，調整時間、彈簧、距離、縮放與緩動曲線。

Figma 重複工作

填充 20 個 starter Bot 卡片，避免 logo、元件、間距與資產不一致。

可帶走的工作流啟發

先做出來再判斷

不必先證明想法能上 roadmap，先做到夠真實再評估。

把 Agent 當團隊設計

用角色分工，而不是把所有任務丟給同一個 AI。

用真實素材提高精細度

不要只產生近似版本，盡量接上產品裡真正使用的素材與元件。

人的判斷仍是核心

AI 沒有取代設計品味，只是給設計師更多使用判斷的機會。

原文整理

xAI 設計師 John Bai 用 Grok Bot 設計 Grok Bot：四個 AI 設計 Agent 怎麼改變他的工作流程，xAI 設計師 John Bai 用 Grok Bot 來設計 Grok Bot 本身。他建了四個 AI 設計 agent：Experiments（探索概念原型）、Motion God（動態設計，可用真實生產素材）、Figma Bro（透過 Figma MCP 精準處理重複生產工作）、Devbot（回答工程問題並輔助其他 agent）。

這四個 agent 可以互相開會、分派工作、整合成果。John 分享了三個案例：用 Experiments 探索三種環境 Bot 入口（Mac 瀏海、角落探頭、游標隨行），用 Motion God 在 localhost 建測試環境搭配真實動畫素材做宣傳影片原型，用 Figma Bro 自動填充 20 個 starter Bot 的卡片元件。

John Bai 是 xAI 的設計師，負責設計 Grok Bot 這個產品。這篇文章講的是他怎麼用 Grok Bot 來設計 Grok Bot 本身。他在 SpaceXAI 的工作是建造能把想法變成實際成品的 agent，而對設計師來說，這改變了「什麼樣的想法值得去探索」這件事的門檻。

他提到設計一直以來都是一個把想法賦予形體的過程：做出來、看反應、修改，直到感覺對了。當「做出來」這件事變得更容易，設計師可以同時探索更多方向、更快做出反應，讓一個想法自己展現它要變成什麼，而不是在開始之前就定義好。

＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿ ▍ Grok Bot 是什麼

Grok Bot 給了 John 一個全天候運作的 AI 設計 agent 團隊，每個 agent 都有自己的電腦。它們有記憶、可以使用工具、可以把工作從最初的想法推進到完成的成品。它們在 John 離開電腦的時候也會繼續工作，這一點很重要，因為靈感常常在離開桌子的時候出現。

＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿ ▍ 四個設計 Agent

John 建了四個各司其職的 bot：

Figma Bro 負責在 Figma 裡處理重複性的生產工作。Motion God 負責幫他做動態原型，他只要用口語描述互動應該是什麼感覺就可以。Experiments 是他拿來把還不確定該變成什麼的想法先具象化的地方。Devbot 負責回答工程問題，同時幫其他 bot 理解一個想法在技術上應該怎麼被實現。

這些 bot 的命名讓各自的角色一目了然，但它們不是各做各的。John 的設計 agent 可以互相開會、把專案的部分工作分派出去，然後把成果帶回來整合。他在文章裡分享了三個最近的實際案例。

＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿ ▍ 案例一：Experiments 探索環境 Bot 入口

John 想探索的第一個方向是怎麼讓 Bot 隨時隨地都能被呼叫。他想試鍵盤快捷鍵、作業系統層級的進入點、以及其他喚起 Bot 的方式，所以他把「探索環境 Bot 存取」這個任務交給了 Experiments。

Experiments 做了三個版本。第一個把 Bot 放在 Mac 的瀏海（notch）位置，在工作時待在固定位置，有事需要注意的時候浮出來，想看更多的時候展開成一個小工作區。這讓 agent 有了一個固定的位置，又不需要多開一個視窗。

第二個版本讓 Bot 在滑鼠移到桌面角落時探頭出來，感覺不像是一個持續存在的介面，更像是一個角色在被呼叫時走進場景。

第三個版本讓 Bot 跟著游標移動，像一個隨行夥伴，跟手上正在做的事情產生更緊密的連結。

John 只是描述了這些行為，Experiments 自己想出怎麼把每一個都做成實體。它把角色動態和轉場分派給 Motion God，桌面行為和實作問題分派給 Devbot，然後把所有東西整合成不同精細度的原型，讓 John 可以實際操作試用。

John 說這就是他保留一個專門的 Experiments agent 的原因。他不需要先判斷一個想法合不合理、可不可行、或是有沒有上 roadmap 的資格，就可以把它做到夠真實來評估。這三個概念沒有一個完全照探索的樣子出貨，但那也不是重點。他有了一個想法，做了三個版本，從每一個版本裡學到東西。

＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿ ▍ 案例二：Motion God 用真實素材做動態

過去做動態設計的時候，John 通常會把想法交給團隊裡的動態專家。他可以描述行為或做幾個關鍵影格的 mockup，但要讓動態真正動起來才能看到效果，這一步以前得靠別人。有了 Motion God 之後，他可以留在探索的循環裡，用感覺來指導互動。

有一次他要為一個 email campaign 製作 Grok Bot 角色的宣傳影片原型。流程很具體：Bot 出現、注意到 app 視窗、然後彈跳到定位。

John 不想讓設計 agent 從截圖重新畫角色或生成一個近似版本，他要 agent 用的是產品裡已經存在、已經會動的那個素材。所以他讓 Motion God 在 localhost 上用實際的動畫規格檔案建了一個測試環境。這樣他可以手動調整時間、彈簧效果、距離、縮放和緩動曲線，而且是在動畫運行的狀態下調整。

但他也發現自己會給出簡短的比較式回饋：「看左下的停頓時間再長一點」「彈跳太誇張了」。Motion God 做出修改後，他可以馬上再看一次整個序列。

John 說這比較接近他設計動態的自然方式。他通常在看到之前不知道一個轉場應該花 280 毫秒還是 340 毫秒，但他知道怎麼描述它，也知道什麼時候感覺剛好對了。

他認為有趣的部分不是 bot 做了一個動畫，而是他可以給 bot 一個真正的生產素材，然後圍繞它建立一個可操作的環境。他可以透過確定性的控制來微調動態，也可以繼續用跟人類協作者一樣的語言來指導 Motion God。

＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿ ▍ 案例三：Figma Bro 處理重複工作

在 Grok Bot 的新手引導流程中，團隊想要展示一些「開箱即用」的 starter Bot，讓新使用者馬上就能派上用場。團隊內部眾包了一份 20 個 bot 的描述清單，像是「Chief of Staff」和「Inbox Triage」這類角色，每一個都需要不同的頭像和對應的屬性。John 在 Figma 裡建了一個 auto-layout 的元件，然後讓 Figma Bro 去填充剩下的。

團隊也想了解新使用者常用哪些工具，好讓他們的第一個 bot 就配備相關的 context。John 做好頁面版型，然後派 Figma Bro 去搜尋正確的 asset 並按使用頻率排列。

這些工作在創意難度上不高，但會消耗創意注意力。這也是小的不一致最容易累積的地方：用錯 logo 版本、套到過期的元件、頭像從不同來源拉、第十張卡的間距跟第一張不一樣。

John 不想讓 Figma Bro 用目測做這些事。透過 Figma MCP，它可以檢視實際的檔案，使用精確的 x 和 y 座標、寬高、間距、字型、填色、描邊和元件結構。如果已經有現成的 frame 或 component，那就是唯一的 source of truth。

＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿ ▍ John 的結論

這些工具沒有讓設計變成一次到位的過程，但它們讓循環變得更緊湊。有了 AI 設計 agent，John 可以更早把想法推到外面的世界、用更高的精細度做回應，把更多注意力花在版本之間的判斷上。Grok Bot 沒有取代那個判斷，它給了他更多使用判斷的機會。
