AI 讓我開始退訂 SaaS：重新計算 Build vs Buy 的分界線

AI 不是讓所有 SaaS 失去價值，而是把「自己做、自己改、自己部署」的門檻往下拉，讓我們必須重新計算 Build vs Buy 的分界線。

來源影片：https://youtu.be/Ugk5OPno-gg?si=7l8cLLeOxWm-fT0P

重點摘要

  • ManyChat 是這支影片的起點。 講者真正需要的功能只是「留言指定關鍵字後自動私訊連結」，但每月要付 69 美金；用 AI 協作後，做出精簡版 ManyChat 的成本下降，這筆帳就變得值得重新算。
  • AI 改變的是 Build 的成本。 以前自己開發可能要兩三天，直接付 SaaS 月費比較合理；現在若一個下午能做出真正需要的 10% 功能，Build 和 Buy 的界線就移動了。
  • 自己做不等於全部從零寫。 一種是叫 AI 幫你做出客製功能；另一種是拿 GitHub 上的開源專案回來架、改、部署。AI 讓看懂 README、Docker、環境變數、port、database、reverse proxy 的門檻變低。
  • 開源不等於整套服務零成本。 程式碼免費，不代表伺服器、第三方 API、搜尋資料、email、簡訊、AI 模型或維護都免費；例如工具可以自架，但資料仍可能依賴 DataForSEO 之類服務。
  • Buy 要算月費之外的隱性成本。 包含席次費、流量費、升級費，以及未來被平台綁定、漲價、API 改規則或功能被砍的風險。
  • Build 也要算完整成本。 包含開發時間、算力、部署、第三方 API、資安、備份、維護，以及最容易被低估的「自己的時間」。
  • Build 常輸在三件事：算力、規模、生態系。 一個人自架便宜，不代表 50 人、100 人使用也便宜；Notion 這類產品的價值也不只是功能，還有模板、教學、整合與團隊習慣。
  • Build 的回報有時不是省錢，而是控制權。 包含資料掌控權、功能選擇權與系統控制權；當資料、程式碼與服務掌握在自己手上，就比較不會完全受平台政策與商業決策牽制。
  • SaaS 仍然有價值。 它把更新、部署、備份、資安、多人協作與生態系包在月費裡；很多情況下直接付錢仍然是最便宜、最安全的做法。
  • Self-hosted 不等於比較安全。 自己架之後，更新、備份、權限、漏洞與監控都會變成自己的責任；新手應先從壞掉也沒關係、沒有重要資料的小工具開始。

一句話總結

AI 不是讓所有 SaaS 失去價值，而是把「自己做、自己改、自己部署」的門檻往下拉，讓我們必須重新計算 Build vs Buy 的分界線。

關鍵觀察

  1. 影片不是單純鼓勵退訂 SaaS，而是提醒每個月固定支出的工具都值得重新檢查：你到底是在買核心價值，還是在為 90% 用不到的功能付費。
  2. AI 讓非工程師也能更接近 Build 選項，但「能做出來」不等於「值得長期維護」。
  3. 對公司導入 AI 平台或內部工具來說，最重要的不是一味自架，而是建立一張決策表：哪些系統應該買、哪些功能可以自建、哪些資料必須掌握在自己手上。

適合使用情境

  • 盤點個人或團隊每月 SaaS 訂閱，找出只用到少數功能、成本卻持續上升的工具。
  • 評估是否用 AI 快速做一個小型內部工具、Cloudflare Worker、自動化流程或開源專案部署。
  • 公司討論「自建 AI 平台」或「內部工具替代外部 SaaS」時，用來建立 Build vs Buy 的成本檢核表。
  • 新手想開始 self-hosted，但需要知道安全、備份、權限與維護責任不是 AI 可以完全代管的。

Build vs Buy 檢核表

  • Buy 成本：月費、席次、流量、升級、平台綁定、未來漲價、API 或功能政策變動。
  • Build 成本：開發時間、AI 協作時間、伺服器／算力、部署、第三方 API、資安、備份、監控、維護、自己的時間。
  • 控制權回報：資料留在哪裡、誰能存取、功能能不能只做需要的 10%、平台停止服務時是否還能持續運作。
  • 不適合 Build 的情況：牽涉公司核心資料、資安要求高、多人規模大、生態系依賴深、壞掉會影響營運，或自己沒有時間維護。

風險提醒

  • 自架服務若處理密碼、客戶資料、公司檔案或營運流程，應先評估資安、備份、權限管理、更新責任與事故處理能力。
  • 不要把重要資料庫或核心系統當作第一個 AI 自架練習專案。
  • AI 可以協助開發與部署，但不能替你承擔系統維運責任。
