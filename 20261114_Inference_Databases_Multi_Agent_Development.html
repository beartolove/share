第一章｜vLLM：把 GPU 資源用在真正需要的推論

1. 從能跑模型，到能服務多個請求

原文以 Hugging Face Transformers 載入模型並提供 HTTP 服務為起點，說明請求增加時，單純逐筆執行可能造成排隊、記憶體浪費與重複計算。vLLM 是大型語言模型推論與服務引擎，提供 OpenAI 相容 API 等介面；它的價值在於記憶體管理與排程，不是讓模型憑空獲得更多算力。「提升數倍」屬來源的概括敘述，並非本次實測或所有模型的保證。

2. KV Cache 與 PagedAttention

自迴歸生成會反覆使用前文的注意力 Key／Value。KV Cache 保留已算過的資料，減少重算，但會占用 GPU 記憶體。PagedAttention 以固定大小區塊管理 KV Cache，透過區塊對照表找到實體位置；隨序列成長按需配置、結束後回收，減少大塊連續配置帶來的浪費。這是資源管理的概念圖解，不是說注意力資料真的成為一般 key-value 資料庫。

3. Prefix Caching、Continuous Batching 與 Chunked Prefill

  • 前綴快取（Prefix Caching）：相同前綴符合快取條件時，可重用已計算的 KV。固定系統提示與共用內容放前方、變動問題放後方，有助於命中。主要節省 prefill，不代表每一步 decode 都因此加速；仍受實際 token、命中率與快取設定影響。
  • 連續批次處理（Continuous Batching）：在生成步驟間調整執行中的請求，已完成者離場、新請求加入，不必等待整批最長的回答結束。但批次變大仍有計算與記憶體成本，不是一次算幾十筆和一筆永遠等時。
  • 分塊預填（Chunked Prefill）：把長提示的 prefill 工作拆開，與其他請求的 decode 交錯排程，以取捨首字延遲、逐 token 延遲及吞吐量。是否預設啟用、可用旗標與具體效果須依版本及模型確認。

4. 部署架構、參數與量測

原文以 API Server → Engine Core／排程器 → GPU Worker → 模型計算，串起請求 token 化、快取查找、區塊分配、批次排程及生成結束後回收。這是簡化架構，實際程序與元件配置依 vLLM 版本而異。

參數 概念與不可省略的限制
--gpu-memory-utilization 此執行個體的 GPU 記憶體使用比例預算，包含權重、執行中需要的記憶體及 KV Cache 等；不是指定比例全數成為 KV 池。原文的 0.92 不當作官方預設值。
--max-model-len 輸入與輸出合計的總上下文上限；調小可限制長請求，但不保證等比例增加並行量。
--max-num-batched-tokens 每次排程的 token 預算，影響 prefill／decode 取捨，不能直接當成每個請求的長度。
--max-num-seqs 同一輪可處理的序列數上限，不等於保證可穩定服務的使用者數。
--kv-cache-dtype、--quantization 分別涉及 KV Cache 與模型量化格式；可用格式、核心與數值品質都取決於硬體、模型及版本。
--tensor-parallel-size、--pipeline-parallel-size 張量平行切分每層運算、流水線平行分配不同層；通訊成本、同步與管線氣泡會影響成效。

原文還提 CPU offload、AWQ、GPTQ、FP8 等方法。CPU offload 可用主記憶體分攤權重，但受 CPU–GPU 傳輸頻寬限制；多卡也不必然降低延遲。量化通常能減少部分記憶體需求，但不保證一定更快、品質無損，或整體占用精確減半。所有參數預設、旗標及硬體支援請以實際安裝版的說明及啟動紀錄為準。

觀察 KV Cache 使用率、等待請求、搶占、快取命中率，並同時量測首字延遲（TTFT）、逐 token 延遲（ITL）、吞吐量與輸出品質；不能只看 GPU 使用率。發現瓶頸後每次只改少量參數、保留對照與回復設定。

第二章｜PostgreSQL：儲存、查詢、共享快取與可靠性

1. 先評估整合需求，不把每個需求都變成一套系統

原文以電商商品、附近門市、全文搜尋及不同來源 JSON 資料為例，對比同時維運 MySQL、Redis、Elasticsearch、MongoDB 等服務的複雜度。PostgreSQL 提供關聯式 SQL、JSON／JSONB、陣列、多種索引與擴充介面，可在合適場景減少外部系統數量；但不表示能全面取代上述產品。地理應用常用 PostGIS、向量搜尋常用 pgvector，兩者屬擴充套件，不應全部寫成 PostgreSQL 核心內建。

2. 資料頁、資料列與索引

資料以頁面為單位讀寫，常見預設頁面大小為 8 KB，可在編譯時調整。資料列稱 tuple；並非每筆資料一定有使用者定義的主鍵。一般 heap 資料表與索引分開儲存，索引項目可指向資料列位置。原文以 B+ 樹與 B-link 觀念解釋樹狀查找及頁面分裂，這是入門簡化；不能據此宣稱所有索引或工作負載都較其他資料庫快。

實體檔名中的 relfilenode 是檔案節點識別，不等同資料表 OID；重建等操作可改變 filenode 而不變 OID。大型關聯檔案常以預設 1 GB 分段，這個分段大小也可在建置時調整。儲存還涉及其他 forks、TOAST、MVCC 等機制，並非圖卡已完整涵蓋。

3. 多程序與共享緩衝區

主控程序（傳統稱 postmaster）接受連線並管理 backend；一般連線會有服務它的後端程序。多連線須評估連線池與程序成本，不應無限制開連線。Shared Buffers 讓程序共用資料頁快取，降低重複磁碟讀取；Buffer Manager 與 Storage Manager 等元件協調頁面存取。

程序分離不等於故障完全隔離：backend 異常崩潰可能使其他連線中斷並觸發重新初始化／復原。不能把「一個程序崩潰，其他連線保證不中斷」當成架構承諾。

4. WAL、髒頁與背景工作

WAL（Write-Ahead Logging，預寫式日誌）的核心約束，是相關日誌先持久化，才允許對應資料頁寫入持久儲存，供崩潰復原重做。提交的持久性取決於 synchronous_commit、fsync 等設定及儲存可靠性。

  • Checkpointer 協調檢查點與必要頁面的寫回。
  • Background Writer 平時協助寫出髒頁，分散部分 I/O 壓力。
  • WAL Writer 背景處理 WAL 寫出，但同步提交所需的 WAL 刷寫也可由提交 backend 負責，不是每次 commit 都交給 WAL Writer；backend 本身也可能因需要空間等原因寫出髒頁。

順序日誌與分散頁面寫入是不同工作；原文的效能倍數屬直覺說明，不是跨磁碟與工作負載的固定比例。

5. SQL 到資料存取：簡化但不漏掉重寫

概念流程可寫為：Parser／語意分析 → Rewrite → Planner／Optimizer → Executor → 存取方法與緩衝／儲存層。規劃器依統計資料與成本估計選擇掃描、連接與索引等計畫，不是任何 SQL 都一定走索引。SELECT 讀取需要的頁面並依可見性規則產生結果；UPDATE 涉及資料版本、WAL 與後續頁面寫回，不能簡化為原地改一個格子便完成交易。擴充介面可加入型別、運算子、索引或其他能力，但仍須管理版本、維運與安全風險。

第三章｜多代理開發：把模糊需求變成可驗收的軟體工作

1. 來源中的 TRAE SOLO 示範

原文提到 TRAE 的 IDE／SOLO 模式，以及由 SOLO Coder 主控產品規劃、UI 設計、開發等代理。TRAE 官方網站可確認產品與 SOLO 名稱；具體模式介面、可選模型、代理呼叫方式與免費方案則屬來源當時敘述，不當作現行免費或所有版本皆可使用的保證。角色分工可能改善工作組織，但沒有本次量測，不能宣稱必然提升準確率。

代理可有相對獨立的上下文，避免所有資訊塞進同一段對話；這是工作脈絡的分工，不是資訊安全隔離。若共用檔案、工具、權杖或工作區，仍可能互相讀取或影響，必須另設權限與敏感資料規則。

2. 需求 → PRD → 原型 → 計畫 → 程式碼

來源示範先建立產品、UI 與開發角色，允許必要的代理呼叫；以自然語言交代需求後，產出 PRD（產品需求規格）及可操作的 HTML 原型，人工檢查功能範圍與預期成果，再使用 Plan 確認工作拆解才執行開發。主控代理負責派工與整合，人仍要負責需求取捨、品質與最終驗收，不是按一次同意就免除責任。

3. MVP 與版本迭代

範例是一個自訂顯示設定的電子書閱讀工具：先完成視窗大小與字體／顏色等 MVP，再分版本加入行距、字距、段落縮排、多書管理與列表，最後討論 TTS 文字轉語音。這裡以合法取得內容的正當閱讀與無障礙產品開發解讀，不鼓勵規避工作管理、偽裝作業或逃避制度；TTS 的費用、授權與隱私也須另行確認。

4. 並行不是放任多個代理修改同一份程式

來源示範把調整拆成多個任務同時進行。實務上需先定義介面、檔案責任與交付契約，使用分支／worktree 或其他受控隔離機制；由單一整合者處理衝突，合併後執行整合測試、回歸測試與安全檢查。V1.1 與 V1.2 若有依賴就不能假定完全平行。可執行成品與測試結果，才是交付證據，代理說「完成」不算驗收。
