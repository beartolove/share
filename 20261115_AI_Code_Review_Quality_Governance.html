核心觀點：多層降低風險，不是保證沒有 bug

AI 生成程式碼愈快，瓶頸愈容易轉移到規格、驗證、審查與上線治理。不要把品質押在最後一個人逐行閱讀；把可執行驗證、CI、AI 與資安審查、依風險核准、合併佇列、漸進發布與事故回饋串成多層防線。每一層都有盲點，多層也不是零缺陷保證。

四階段流程速覽

階段 檢查與行動 應留下的證據
PR 前 讓 AI 實際執行產品，再用全新上下文的 Agent 檢查變更 命令、測試輸出、建置結果、瀏覽器操作與截圖
PR 中 CI、AI 審查、獨立資安審查、依風險人工核准四關 自動檢查結果、每條意見的處理理由、對應 commit 的核准
合併時 Merge Queue 把候選變更套到最新主分支，再跑檢查 針對最新整合狀態的測試結果
合併後 功能開關、內部先用、漸進發布、持續監控與復原 遙測、值班與責任人、關閉開關／修正發布／回復方案

第一階段：PR 前，讓 AI 能驗證，也讓審查相對獨立

  1. 驗證產品真的能運作。 給 Agent 可執行的測試、建置、瀏覽器與模擬器等工具；要求呈現實際輸出，不能只說「完成了」。UI 變更也需與設計、使用流程比對。
  2. 全新上下文審查。 讓另一個 Agent 取得目標、規格、程式碼變更與必要專案脈絡，減少沿用開發者既有推論的偏誤。但獨立上下文不保證客觀，不等於安全隔離；仍可能共享模型盲點、錯誤規格或受不可信內容影響。
  3. 把重複意見變成規則。 官方文章提到短版 CLAUDE.md 說明技術棧、慣例與目標；REVIEW.md 定義具體失敗模式、嚴重度與證據要求。可機械檢查的問題優先交給 Lint、測試與 hooks。

第二階段：PR 中的四道關卡

一、CI： 自動執行 Lint、型別檢查、多平臺測試與建置。工具能判斷的問題先自動化；通過只代表這些檢查沒發現問題，不代表需求完整或系統安全。

二、AI 審查：發現 → 篩選 → 處理。

  1. 發現問題： 對照 PR 的目的、整個程式庫與相關呼叫端，檢查是否解決需求、是否符合系統、是否破壞其他行為；修 bug 時要追根因。
  2. 篩選問題： 多個 Agent 並行找問題，再由其他 Agent 驗證／投票；降低誤報，過濾只涉及風格或清理的低價值意見。不能只追求留言數。
  3. 處理問題： 以 Important、Nit、Pre-existing 區分嚴重度與既存缺陷。每條意見都要修正，或附理由結案；不是把 AI 建議一律照單全收，也不能靜默略過。依團隊規則，未解決的 bug 或資安討論會阻擋合併。

三、獨立資安審查： 另跑安全導向自動審查；需要修正或附合理理由處理發現項目。自動資安工具不能取代威脅建模、權限設計與必要的人工檢查。

四、依風險人工核准： 官方文章中的低／中／高風險分別為 0／1／2 位人類核准，是該團隊特定時點的策略，不是通用合規標準。低風險輕量路徑還受信任作者名單、第二分類器與敏感路徑規則限制；AI 的核准不算人的核准。CI 工作流程與指定敏感路徑仍需人員把關；新 commit 可能需要重新核准。內部功能不必然低風險，仍應看資料、權限、金流與影響範圍。

AI 審查品質：真實事故評測＋無效意見，兩個指標一起看

  • 找得到真實缺陷： 收集造成線上事故的 PR、修正與回復紀錄，請熟悉系統的工程師確認 bug 與位置；固定案例集每日評測。調整提示詞、工具或模型後，在同一組案例比較檢出表現，不把報得多當成能力好。影片以命中記 1、漏掉記 0 解釋，屬簡化示例，不是本次重跑實驗。
  • 不要製造噪音與有害修正： 官方按作者的反應分類：已修、認為錯誤、刻意如此、不值得改；並對已知乾淨 PR 測試是否提出可能導致有害修改的意見。作者沒採用不必然代表意見無效，可能是取捨、時間或漏判；「已知乾淨」也不是絕對沒有 bug 的真值。需人工抽查與追蹤後續結果，不能機械地把後三類全部判成誤報。
  • 以實際結果護欄： 同時追蹤審查輪數、人類等待與核准負擔，以及回復率和事故率，避免只是把審查成本移成事故處理成本。

防止 AI 互改到天亮：四項收斂規則

  1. 三輪仍未通過，停下來重想方法。 提醒作者重新檢視整體設計，而非無限微修；官方記錄曾有 PR 一夜超過五十輪。
  2. 前幾輪看整體，後續聚焦新增 diff。 降低每輪重新挖出舊問題的噪音；只看增量不是不漏缺陷保證。敏感、高風險與跨模組變更仍應全局檢查並重跑適當測試。
  3. 同類錯誤一次列出。 要求修正所有同類實例，不只標一行，避免下一輪逐一冒出。
  4. 已提出的發現不重複發布。 追蹤既有討論、修正與理由，不把相同意見反覆當新問題。

第三階段：合併佇列，檢查「合在一起」是否成立

PR 各自通過不代表彼此相容。Merge Queue 在最新 main 上套用候選變更、重新檢查，處理與其他 PR 的交互影響；失敗就退回處理。它只能覆蓋實際測試到的條件，不保證主分支永遠正常。

第四階段：合併後，限制影響並縮短發現與復原時間

  • 功能開關與內部先用： 新行為先藏在 flag 後，優先讓內部使用者發現回歸；內部使用不能代表所有真實使用情境。
  • 逐步上線： 官方 2026-10-15 文章確認先 latest、後 stable，但沒有承諾固定等待天數。影片說約一週，是影片當時的敘述，不當成目前或未來版本的服務保證；實際週期以當版發布政策為準。
  • 監控、修正與回復： 作者、值班人員與遙測共同觀察；可先關 flag，必要時修正發布、回復 commit 或重建版本。Feature flag 只能控制後續路徑，不能自動復原已寫入資料、已發通知、交易或外部副作用；另需資料復原與補償方案。

人仍需承擔的五項責任

  1. 決定做什麼： 產品方向、品味、範圍與驗收規格；AI 可協助分析，但須有人對取捨負責。
  2. 審查高風險程式碼： 計費、權限、自動更新與 CI／發布流程等高衝擊變更。
  3. 把關架構： 特別是會成為後續人與 Agent 仿效範本的設計。
  4. 閱讀證據： 實際命令、輸出、測試與畫面；追問檢查沒涵蓋什麼，不把摘要或核准勾選當作充分證明。
  5. 為上線結果負責： 明確責任人、值班、事故復盤與修復；不能把責任推給產生程式碼的模型。

可落地的第一步

先選一個程式庫：短版專案規則、可執行測試、PR 模板的 Testing／Risk／How to revert、CI 必過、每條意見有結案理由、敏感路徑人工核准，再逐步加入 AI 審查與事故評測。以人類投入、漏檢、噪音與事故護欄決定是否擴大，不追求一次取消所有人工審查。
